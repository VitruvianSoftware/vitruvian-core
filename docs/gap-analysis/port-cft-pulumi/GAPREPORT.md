# Pulumi Foundation Ports — Gap Report vs `terraform-example-foundation`

_Functional gaps between Google's `terraform-example-foundation` and its two Pulumi ports (`pulumi_go-example-foundation`, `pulumi_ts-example-foundation`) and their shared `pulumi-library`. Every gap below was produced by a per-stage/per-dimension finder, then confirmed by an independent adversarial verifier tasked with refuting it, then spot-checked by a completeness critic. Near-identical findings from different finders are merged (marked “corroborated by N finders”)._

**236 confirmed gaps** — 23 critical, 94 major, 100 minor, 19 info. By port: 87 TS-only, 63 Go-only, 86 both. (10 additional claims were investigated and refuted; they are listed at the end and excluded from these counts.)

Severity: **critical** = deployment fails or a security control is silently absent; **major** = meaningful feature/resource missing; **minor** = small option/output/validation missing; **info** = worth knowing, non-blocking. Where a verifier judged the finding's own framing or severity to need qualification, that is carried as a _Verifier note_.

## Critical (23)

### 0-bootstrap

- **[TS] Authoritative projectCreator enforcement (org_project_creators) missing** — _0-bootstrap_
  - The TF foundation's core bootstrap security control — an authoritative IAM binding restricting roles/resourcemanager.projectCreator at the org/parent-folder level to only the 5 step service accounts + org admins group (removing all other members) — has no TS equivalent. TF main.tf's comment explicitly calls this enforcement out. The Go port implements it (sa.go section 9, bindParentIAMBinding "org-project-creators"), so this is also Go/TS drift. Without it, any default org-wide projectCreator grants remain in place silently.
  - **Evidence:** TF: terraform-example-foundation/0-bootstrap/main.tf lines 20-30 + upstream terraform-google-bootstrap v12 main.tf google_organization_iam_binding.project_creator / google_folder_iam_binding.project_creator. Checked: pulumi_ts-example-foundation/0-bootstrap/index.ts, sa.ts, config.ts and pulumi-library/ts/packages/bootstrap/src/bootstrap.ts — no projectCreator binding anywhere (grep only matches README prose).

### 1-org

- **[GO] KMS org service agent never provisioned; org-level IAM binding targets nonexistent principal** — _1-org_
  - Upstream commit 1edf793 (enable kms centralized key usage tracking) creates the ORG-level KMS service agent via 'gcloud beta services identity create --service cloudkms.googleapis.com --organization <org_id>' before granting roles/cloudkms.orgServiceAgent to service-org-<org_id>@gcp-sa-cloudkms.iam.gserviceaccount.com. The TS port does this correctly with a command.local.Command running the org-level gcloud command (iam.ts:194-205), so this is Go-only drift.
  - **Evidence:** TF: terraform-example-foundation 1-org/envs/shared/iam.tf module.create_kms_organization_service_agent + google_organization_iam_member.kms_usage_tracking (commit 1edf793). - **[GO] Access Context Manager policy created twice with the same Pulumi resource name — pulumi up fails** _(corroborated by 2 finders)_ — _1-org/org_policy_

- **[TS] Default compute service account is never deprivileged on any 1-org project** — _1-org/projects_
  - Terraform sets default_service_account = "deprivilege" on all seven 1-org project-factory modules, stripping the Editor role from each project's default compute SA. ### 3-networks-hub-and-spoke

- **[GO] All spoke environments hardcode identical subnet CIDRs — second spoke peering to the hub fails** — _3-networks-hub-and-spoke_
  - The spoke branch hardcodes 10.8.64.0/18 and 10.9.64.0/18 primaries, 10.26.2.0/23 / 10.27.2.0/23 proxy subnets, and 100.72-75.64.0/18 secondary ranges for every environment stack; there is no config key to override them. In TF each env uses distinct ranges (dev 10.8.64.0/18, nonprod 10.8.128.0/18, prod 10.8.192.0/18, etc.). Because GCP rejects VPC peering when a new peer's subnets overlap those of an already-peered network, deploying the second and third spoke against the shared hub fails. TS varies CIDRs per env directory.
  - **Evidence:** Port: pulumi_go-example-foundation/3-networks-hub-and-spoke/main.go:234-269 (hardcoded spoke subnets), loadNetConfig has no subnet range config. TF: 3-networks-hub-and-spoke/envs/{development,nonproduction,production}/main.tf subnet_primary_ranges differ per env. TS: pulumi_ts-example-foundation/3-networks-hub-and-spoke/envs/*/index.ts uses 10.0.64/21, 10.0.128/21, 10.0.192/21.
  - **Verifier note:** The mechanism described ("peering fails") is likely slightly overstated — GCP's peering-creation overlap check is pairwise between the two directly-peered networks, and the hub's own ranges never overlap the spokes', so the pulumi/gcloud calls to create the 2nd/3rd spoke peering would probably succeed rather than hard-error. The real-world consequence is silent/non-deterministic routing ambiguity between spokes that share identical CIDRs behind the same hub (GCP resolves same-destination overlaps via an internal, non-configurable algorithm) plus meaningless hub BGP aggregate-route advertisements of 10.8.0.0/16 and 10.9.0.0/16 that now cover all three identical spoke subnets. That's still a critical, ship-blocking networking defect for a multi-env foundation — just via broken/ambiguous traffic routing rather than an outright deploy-time rejection.

### 3-networks-svpc

- **[GO] VPC-SC perimeter silently skipped (and exports break) when policy_id config is unset** — _3-networks-svpc/vpc_sc_
  - TF requires access_context_manager_policy_id and always creates the access levels and a dry-run service perimeter. The Go port only creates the perimeter if cfg.PolicyID != ""; all shipped stack config examples (Pulumi.development/nonproduction/production.yaml.example) omit policy_id, so out-of-box deployments get no perimeter at all — a security control silently absent. Additionally, in that branch accessLevelName/accessLevelDryRunName are left as zero-value pulumi.StringOutput and are still exported, which fails/panics at runtime (uninitialized Output), so the default-config deployment likely errors.
  - **Evidence:** TF: 3-networks-svpc/envs/production/variables.tf (access_context_manager_policy_id required), modules/shared_vpc/service_control.tf (perimeter always created). Go: /home/user/pulumi_go-example-foundation/3-networks-svpc/main.go lines 258-294 (if cfg.PolicyID != "" ... else only perimeterName set) and Pulumi.*.yaml.example (no policy_id key).
  - **Verifier note:** Gap is real but severity is high, not critical, and the runtime-failure half of the claim is wrong. (1) Exporting the uninitialized StringOutputs does not panic or error in SDK v3.231.0 — nil OutputState awaits as unknown and the stack exports are just blank/absent; verified empirically. (2) Out-of-box Terraform creates only a dry-run (monitoring, non-enforcing) perimeter since enforce_vpcsc defaults to false in modules/shared_vpc/variables.tf:182-186; enforcement is opt-in in both implementations. The silently missing control in a default deployment is therefore the dry-run perimeter plus pre-provisioned access levels, not an enforced boundary.
