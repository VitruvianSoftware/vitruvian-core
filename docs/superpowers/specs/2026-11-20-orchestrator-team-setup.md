# Orchestrator: set up and sync a repository's team (step 3 of 5)

Step 3 of 5 in making `vitruvian-orchestrator` a public plugin (1: team file #5223,
2: generic team #5228, 4: native engine #5241). Today a stranger has to hand-write
`.agents/team.json`, and a model they set there only reaches the harness at dispatch time,
which OpenCode cannot do at all (its Task tool has no model override). This step adds two
actions, in all three plugins, behind one new tool and one new skill.

## `init`: write a starter team file

Creates `<root>/.agents/team.json` when it does not exist:

```json
{
  "$schema": "https://vitruviansoftware.dev/schemas/orchestrator-team.json",
  "notes": "",
  "roles": {}
}
```

- Every role resolves to the plugin's generic agent, native engine, until the user edits it.
- Refuses when the file exists (no overwrite flag; the user deletes it or edits it).
- Optional `agents: ["developer", …]` (roles, not `lead`): also copies those roles' generic
  agent files from the plugin into the **calling harness's** agent folder as editable starter
  agents named `team-<role>` (Claude Code `.claude/agents/team-<role>.md`, OpenCode
  `.opencode/agents/team-<role>.md`, Antigravity `.agents/agents/team-<role>.md`), with the
  `name:` line rewritten, and maps each role to it (`roles.<role>.agent = "team-<role>"`) with
  `"engine": "native"` on the row. The `team-` prefix avoids clashing with the plugin's own
  role-named agents in harnesses that do not namespace plugin agents. Refuses when any
  target file exists. Writes nothing unless every check passes (all-or-nothing).

## `sync`: apply the team file's models to the repository's agent files

For every role whose row is `source: "team"`, find that agent's file for each harness that
has one in the repository, and set its model lines from the team file's **explicit**
harness values (role, then team tier), never from plugin defaults:

| Harness | File | Lines set |
|---|---|---|
| Claude Code | `.claude/agents/<agent>.md` | `model:`, `effort:` |
| OpenCode | `.opencode/agents/<agent>.md` | `model:`, `reasoningEffort:` |
| Antigravity | `.agents/agents/<agent>.md` | `model:` (must be `inherit`, `flash` or `pro`; any other value is reported and skipped, since Antigravity silently drops such a file) |

- Only the YAML frontmatter's own lines change; the body and every other key are left
  byte-identical. A missing line is added at the end of the frontmatter; a role with no
  explicit value for a harness leaves that file alone.
- A file with no frontmatter, a symlink, or a path that resolves outside `<root>` is
  reported and skipped.
- `check: true` changes nothing and reports each file that would change (for CI); the
  result says `changed` / `unchanged` / `skipped (<reason>)` per file.
- A file whose first lines carry a "Generated by … Do not edit" comment is skipped as
  `generated`, so sync never fights a generator. vitruvian-core's named agents are
  generated and its team file sets no harness models, so sync is a no-op there (test).

## The tool and the skill

- Tool `team_setup` in all three plugins: `{ action: "init" | "sync", root, agents?, check? }`.
  `root` must be an absolute directory (same rule as the `team` tool). It writes only
  `.agents/team.json` and agent files under the three agent folders inside `root`,
  never follows symlinks, and validates every role and agent name against the existing
  role set and agent-name pattern. Returns a per-file report.
- Skill `team-setup` (user-invocable, e.g. `/vitruvian-orchestrator:team-setup` in Claude
  Code) in each plugin: asks which action, explains what each does in two lines, calls the
  tool with the repository root, shows the report, and for `init` points at the guide.
  Generated from one roster source per harness like the `orchestrate` skill, under the same
  no-repo-specifics drift test.

## Core

Pure functions in `packages/orchestrator-core`, vendored like the rest:
`renderStarterTeam()`, `starterAgentFile(text, role)`, and
`applyAgentModels(text, harness, { model, effort })` → `{ text, changed, reason }`.
File access lives in each plugin's tool handler. Tests cover: frontmatter edits keep
everything else byte-identical, CRLF files, missing lines added, no frontmatter, the
generated-comment skip, Antigravity value rule, model charset rule (same as the team
file), init refusing to overwrite, all-or-nothing on a partial conflict, symlink and
outside-root refusal, `check` writing nothing.

## Out of scope

Publishing (step 5). Editing anything except model/effort lines.
